# 전체 화면 반응형 UI 실사용 점검

검증일: 2026-10-26. 앱 코드는 수정하지 않았다. 아래 7건 중 1~6은 재현한 문제이며, 7은 여백 개선 제안이다. 수정은 사용자 선택·승인 후 별도로 진행한다.

## 실행한 검증

- Windows Chrome 155.0.8059.85의 실제 렌더러를 headless 모드로 실행했다. 별도의 임시 프로필과 로컬 서버에서 **현재 배포본 dist**를 열었다.
- 홈·시험·통계·더보기·자료 상세를 320 / 375 / 430 / 680 / 768 / 1023 / 1024 / 1280 / 1440 / 1920px에서 확인했다.
- CSS 뷰포트를 320→1920→320px로 **16px 간격** 변경하고, 360·430·680·768·1024·1151·1400px 주변은 1px 단위 경계도 별도 확인했다. 모든 픽셀을 연속 측정했다는 뜻은 아니다.
- 별도로 Chrome 창 자체를 약 40px 간격으로 넓혔다 좁혔다. Chrome의 창 최소 크기로 실제 콘텐츠 너비는 **512~1920px**였다. 320~430px 검증은 뷰포트 에뮬레이션으로 구분한다.
- 680 / 1024 / 1440 / 1920px 기준 창에서 **실제 Chrome 기본 페이지 확대 설정**을 80 / 90 / 100 / 110 / 125 / 150 / 200%로 변경했다. CSS zoom이나 단순 스크린샷 축소를 사용하지 않았다. getDefaultZoom과 실제 innerWidth·devicePixelRatio를 기록했다.
- 예: 1024px 창은 100%에서 CSS 너비1024px, 200%에서512px. 1440px 창은200%에서720px이었다. 확대 때문에 CSS 너비가1024px 아래로 내려가 하단 탭바로 바뀌는 것은 기존의 정상 정책이다.
- 모달15종을 320×400 / 375×600 / 430×840 / 680×400 / 768×600 / 1024×400 / 1440×900에서 열었다. 학습 계획·진도·복습·자료 수정·메모·복습량·복습일·설정·보관함·자료 관리·오늘 복습·시험 수정·중단·마무리·재응시를 포함한다.
- 높이300px의 화면, 목록 끝으로 이동, 모달 내부 스크롤, 실제 휠 입력도 확인했다. 시험 연결 자료 펼침, 자료 상세 기본/복습 탭, 통계 주간/월간/3개월/6개월과 긴 이름도 추가 확인했다.
- 합성 자료18개(활성6·보관12), 시험5개, 공백 없는 긴 영문 자료명과 긴 한글 시험명을 사용했다. 사용자 저장 자료는 읽거나 변경하지 않았다.
- 총 **2,092개 측정 기록, 159장 스크린샷**을 남겼다. 수집한 최종 실행에서 런타임 오류와 누락 리소스는 없었다. UI가 모두 정상이라는 뜻은 아니다.

## 재현 수치와 화면

**R1 — 짧은 모달.** 320×400px에서 시험 마무리 dialog 하단은 y388px인데 버튼 하단은 y431.56px이다. 목록 아래와 설명 위도 약41px 겹친다. 일반 휠로 바깥 dialog는 스크롤되지 않았고, 버튼 중심 hit-test도 실패했다. 코드의 scrollIntoView로 강제 이동하면 버튼이 보이는 경우와 구분했다. 이 강제 이동을 사용자 스크롤 성공으로 판정하지 않았다. 중단 모달도 목록과 설명이 약44px 겹쳤다.

- [비교: 같은 화면320×600](evidence/responsive-audit/wheel-exam-archive-320x600.png)
- [문제: 시험 중단320×400](evidence/responsive-audit/wheel-exam-pause-320x400.png)
- [문제:1024px 창200% 시험 마무리](evidence/responsive-audit/zoom-modal-exam-archive-1024-200.png)

**R2 — 배너.** 767px 화면에서 배너는752px, 배경 이미지 왼쪽은 x115.39px였다. 왼쪽 약115px에는 배경 풍경이 없다. 바로 다음768px 화면에서는 배경 크롭과 로고 폭이 바뀐다. 데스크톱 배너 높이 자체는210px로 유지되어 과거의 큰 높이 증가는 재현하지 않았다. 오두막·곰은 대표 데스크톱 화면에서 유지됐지만 중간 너비 로고/배경의 연결은 개선이 필요하다.

## 유지가 확인된 동작

- 1024px의 PC 사이드바/모바일 하단 내비게이션 전환은 유지됐다. 낮은 PC 창에서는 사이드바 안에서 스크롤할 수 있었다.
- 더보기 메뉴는 PC 구간에서 높이60px·글자14px·아이콘21px 기준을 유지했다. 두 자릿수 보관함 배지도 확인했다.
- 학습 계획 모달은 내용에 맞춰 줄어들고, 낮은 화면에서 내부 스크롤로 버튼에 접근할 수 있었다.
- 기본 홈 카드와 자료 상세의 긴 이름은 대체로 줄바꿈됐다. 문제는 위에 기재한 특정 목록/모달이었다.
- 브라우저 확대 시 실제 CSS 너비에 따라 재배치됐으며, 가로 스크롤 문제는 특히 긴 이름이 있는 펼친 목록과 통계·일부 모달에서 나타났다.

## 실행하지 못한 검증과 한계

- 실제 iPhone Safari, WebKit 엔진, iOS 주소창 접힘/펼침, 안전 영역, 소프트 키보드와 핀치 줌은 실행하지 못했다. Chrome 좁은 뷰포트 결과를 Safari 성공으로 간주하지 않는다.
- 눈에 보이는 Windows 데스크톱 창을 마우스로 직접 잡아 끄는 수동 검증은 하지 않았다. headless Chrome의 실제 창 크기 API와 뷰포트 에뮬레이션을 사용했다.
- 실제 사용자 자료·기기 설정·배포 서버의 결과는 이번 범위가 아니다.
- 테스트 스크립트에서 잘못 지정한 통계 기간 키로 한번 중단된 실행은 앱 결함으로 집계하지 않았다. 실제 UI의 week/month/quarter/half 키로 재실행한 최종 결과만 위에 기록했다.
- 변경은 증거·보고서·스킬 로그에 한정했다. 앱·에셋·PWA·빌드 결과는 수정하지 않았다. source-before.json과 source-after.json 해시 비교 참조.

## 후속 승인 수정 결과

사용자 승인 후 R1·R3~R7을 실제 수정하고 재검증했다. R2는 별도 카메라 미리보기만 제작해 적용 승인을 기다린다. [최신 수정 보고서](responsive-ui-fixes.md)와 [수정 전후 비교](evidence/responsive-fixes/index.html) 참조. 위 내용은 수정 전 점검 이력으로 보존한다.
