# 학습 진도 관리 앱

> 공부한 위치와 회독, 부분 복습 내역을 간편하게 기록하고 여러 학습 자료의 진행 상황을 한눈에 확인하는 웹앱입니다.

## 1. 제작한 것 소개

### 제작 배경과 목적

전공 공부와 자격증·시험 준비를 병행하면서 교재, 문제집, 인터넷 강의 등의 진행 상황을 각각 기억하기 어렵다는 문제에서 출발했습니다. 복잡한 시간표를 작성하기보다는 **공부를 마친 뒤 현재 위치를 빠르게 입력하고, 전체 진행률과 반복 학습 현황을 확인하는 것**을 목표로 기획했습니다.

### 주요 기능

- **학습 자료 관리:** 자료명, 유형, 학습 단위, 전체 분량 등록·수정·삭제
- **학습 진도 기록:** 공부 날짜와 도달 위치 기록, 공부량 및 진행률 계산, 기록 수정·삭제
- **회독 관리:** 회독 완료 표시, 다음 회독 시작, 이전 회독별 기록 조회
- **부분 복습 관리:** 날짜와 복습 시작·끝 위치 기록, 수정·삭제 및 횟수 집계. 전체 진도와 회독에는 영향을 주지 않음
- **진행 현황 확인:** 자료별 진행량·진행률·회독을 카드와 진행률 막대로 표시
- **로컬 저장:** 브라우저 LocalStorage를 활용한 기록 유지

### 기술 스택 및 실행 환경

| 구분 | 내용 |
| --- | --- |
| 프런트엔드 | HTML, CSS, JavaScript |
| 데이터 저장 | 브라우저 LocalStorage |
| 화면 | 모바일 우선 반응형 웹 |
| 디자인 | 화이트, 세이지/그린 계열, LINE Seed Sans KR |
| 버전 관리 및 제출 | GitHub |

**실행 방법:** GitHub에 업로드한 프로젝트의 웹페이지 주소(GitHub Pages 등)를 열거나, 소스코드를 내려받아 웹 브라우저에서 실행합니다. 배포 주소와 실행 시 주의사항은 실제 구현·배포 후 기입합니다.

- GitHub 저장소: `[저장소 주소 입력]`
- 실행 링크: `[배포 주소 입력]`
- 대표 화면: `[완성 후 스크린샷 삽입]`

> **작성 상태 안내:** 이 문서는 제공된 PRD와 개발 계획을 토대로 작성했습니다. 위 기능들은 **구현 목표**를 포함하며, 실제 완료 여부는 코드 테스트 후 확인해 표시해야 합니다.

## 2. PRD — 프로젝트 요구사항 정의서

### 0. AI 개발 담당자에게 보내는 요청

1. 아래 요구사항을 읽고 이해한 내용을 3~5줄로 요약해 확인받습니다.
2. 불명확하거나 결정이 필요한 부분은 작업 시작 전에 질문합니다.
3. 확인 이후 단계별 구현 계획을 제시하고, 승인받은 뒤 개발합니다.
4. **범위 제외 기능은 별도 요청 전까지 구현하지 않습니다.**

### 1. 프로젝트 개요

- **프로젝트 이름:** 학습 진도 관리 앱
- **한 줄 소개:** 학습 상황을 기록하고 한눈에 확인할 수 있도록 하는 앱
- **만드는 사람:** 개인 프로젝트
- **완성 목표:** 수업 과제 제출일까지

### 2. 제작 목적

자격증과 여러 시험을 준비하면서 학습 자료가 다양해졌고, 각 자료의 진행 상황을 한눈에 파악하기 어려워졌습니다. 이를 해결하기 위해 학습 내용을 정리하고 현재 진도와 반복 학습 정도를 쉽게 확인할 수 있는 앱을 제작합니다.

### 3. 대상 사용자

- **주 사용자:** 전공 공부, 시험, 자격증을 준비하는 대학생과 취업 준비생
- **사용 환경:** 스마트폰 및 PC 웹 브라우저
- **사용 특성:** 계획을 복잡하게 세우기보다 공부 후 빠르게 기록하고 전체 현황을 확인하고자 함

#### 3-1. 대표 사용자 페르소나

- **이름/나이:** 김민지 / 23세 대학생
- **상황:** 전공 시험과 자격증을 준비하며 교재, 문제집, 인터넷 강의를 반복 학습
- **바라는 점:** 얼마나 진행했는지, 몇 번 반복했는지 쉽게 확인
- **불편한 점:** 복잡하고 번거로운 공부 기록 과정

### 4. 핵심 기능

#### 4-1. 학습 자료 등록·관리

- 자료 이름 등록
- 학습 유형 선택: **교재, 문제집, 인터넷 강의, 단어 학습, 기타**
- 유형에 따른 학습 단위 선택
  - 교재/책: `Page`, `Chapter`
  - 문제집: `Page`, `문제`
  - 인터넷 강의: `강`, `Chapter`
  - 단어 학습: `단어`, `Day`
  - 기타: 사용자 직접 입력
- 전체 학습 분량 입력
- 자료 수정 및 삭제

#### 4-2. 학습 진도 기록·확인

- 현재 공부 위치와 공부 날짜 입력
- 이전 위치와 현재 위치의 차이로 공부량 계산
- 현재 진행량, 진행률 및 회독 횟수 표시
- 날짜별 학습 기록 확인
- 학습 기록 수정·삭제 시 진행 상황 재계산

#### 4-3. 회독 관리

- 전체 분량 학습 시 현재 회독 완료 상태 표시
- 완료한 회독의 기록 유지
- 다음 회독을 진도 0부터 시작
- 회독별 진행 상황 및 기록 확인

#### 4-4. 부분 복습 관리

- 자료별로 **복습 날짜, 시작 위치, 끝 위치** 기록
- 입력한 복습 구간이 자료의 전체 범위 안에 있는지 확인
- 부분 복습 기록 조회·수정·삭제
- **기록 1건을 부분 복습 1회로 집계**
- 부분 복습은 별도 기록으로 관리하며, **전체 진도·진행률·회독 횟수를 변경하지 않음**

### 5. 범위 제외 — 이번 버전에서 만들지 않는 기능

- 공부시간 측정 타이머
- 하루 권장 학습량 자동 계산
- 회원가입 및 로그인
- 서버 기반 데이터 동기화
- 알림 및 푸시 알림

### 6. 디자인 방향

- 깔끔하고 차분한 학습 관리 화면
- 화이트 배경, 세이지/그린 계열 포인트 색상
- **LINE Seed Sans KR** 폰트
- 둥근 카드, 적절한 여백, 부드러운 그림자
- 진행률을 보여주는 Progress Bar
- 모바일에서도 누르기 쉬운 버튼 크기
- 장식보다 학습 현황 정보의 가독성 우선

### 7. 기술 조건

- HTML, CSS, JavaScript 기반 반응형 웹앱
- 브라우저 LocalStorage 저장
- 새로고침 및 브라우저 재실행 후 기록 유지
- 스마트폰·PC 양쪽에서 화면과 기능 정상 동작
- 모바일 우선 설계

### 8. 기본 가정

- 자료별 전체 학습 분량은 숫자로 표현할 수 있음
- 하나의 자료는 하나의 학습 유형과 단위를 사용함
- 선택 유형에 적합한 학습 단위를 제공함
- 기타 유형은 직접 단위 입력 가능
- 회독은 자료 전체 범위를 한 번 학습한 것을 뜻함
- 공부 후 사용자가 현재 위치를 직접 입력함
- 로그인이나 여러 기기 간 실시간 공유는 필요하지 않음

### 9. 결정한 사항과 검토할 점

**이번 구현 계획에서 채택한 사항**

- 진도는 `+30` 같은 증가량보다 **현재 도달 위치를 직접 입력**하는 방식 사용
- 부분 복습을 별도로 기록하며 1건을 1회로 계산
- 회독 완료 시 100% 상태를 유지하고 **다음 회독 시작** 버튼 제공

**추가 검토가 필요한 세부 사항**

- 과거 학습 기록을 수정할 때 날짜가 뒤섞인 경우 진도를 재계산하는 규칙
- 기록 수정·삭제로 완료된 회독의 전체 분량 도달 상태가 달라질 때 처리 방식
- 전체 분량 또는 단위 수정 시 기존 기록을 어떻게 유지할지

### 10. 완성 기준

- [ ] 자료 등록·수정·삭제가 가능하다.
- [ ] 유형별 학습 단위를 선택하고 기타 단위를 직접 입력할 수 있다.
- [ ] 진도 기록을 추가·수정·삭제할 수 있다.
- [ ] 진행량과 진행률이 정확히 계산된다.
- [ ] 현재 회독 수가 표시된다.
- [ ] 완료 후 다음 회독을 시작할 수 있다.
- [ ] 이전 회독 기록이 유지되고 조회된다.
- [ ] 여러 자료의 진행 상황을 한눈에 확인할 수 있다.
- [ ] 부분 복습을 날짜와 시작·끝 위치로 등록·수정·삭제할 수 있다.
- [ ] 부분 복습 횟수가 정확하며 기존 진도·회독에 영향을 주지 않는다.
- [ ] 브라우저 재실행 후 데이터가 유지된다.
- [ ] 스마트폰과 PC에서 주요 기능이 정상 동작한다.

- [ ] 제외-1. 공부시간 측정 타이머 — 구현하지 않음
- [ ] 제외-2. 하루 권장 학습량 자동 계산 — 구현하지 않음
- [ ] 제외-3. 회원가입·로그인 — 구현하지 않음
- [ ] 제외-4. 서버 기반 데이터 동기화 — 구현하지 않음
- [ ] 제외-5. 알림·푸시 알림 — 구현하지 않음

## 4. 바이브코딩 방법론 비교 — 한 줄 요청 vs PRD

| 비교 항목 | 한 줄 요청 방식 | PRD 방식 |
| --- | --- | --- |
| 진행 방법 | 짧은 자연어 명령으로 곧바로 제작 요청 | 목표·사용자·기능·제외 범위·검증 기준을 문서화하고 단계별 개발 |
| 장점 | 시작이 빠르고 아이디어를 즉시 확인하기 좋음 | 요구사항이 명확하고 기능 누락·범위 확장을 줄이기 쉬움 |
| 단점 | 빠뜨리는 기능이 생기거나 해석이 달라질 수 있음 | 문서 작성에 시간이 들고 초기 결정이 필요함 |
| 수정·확장 | 빠른 실험에 편리하지만 변경 사항을 추적하기 어려울 수 있음 | 변경 근거와 작업 순서를 체계적으로 관리하기 좋음 |
| 적합한 상황 | 간단한 화면 실험, 일회성 프로토타입 | 여러 기능이 연결된 과제, 유지보수가 필요한 앱 |

### 프로젝트에 적용한 관점

이 앱에서는 **진도 기록, 회독, 부분 복습이 서로 어떻게 영향을 주는지**가 특히 중요합니다. 예를 들어 부분 복습을 입력해도 전체 진도와 회독은 바뀌면 안 됩니다. 한 줄 요청만으로 개발하면 이런 규칙을 빠뜨릴 수 있으므로, PRD에서 데이터와 동작 규칙을 먼저 정의하고 TODO로 구현 단계를 쪼개는 방식이 유리합니다.

반면 작은 버튼 배치나 카드 여백처럼 기능에 영향이 적은 시각적 실험은 짧은 요청으로 여러 안을 빠르게 비교할 수 있습니다. 따라서 **초기 아이디어·화면 탐색에는 짧은 요청, 실제 구현과 검증에는 PRD+TODO**를 활용하는 혼합 방식이 적합하다고 판단했습니다.

> 이 비교는 프로젝트 특성에 근거한 **방법론 평가**입니다. 두 방식으로 동일한 조건의 실험을 수행해 얻은 정량적 성능 결과는 아닙니다.

## 5. 개선에 필요한 점

1. **기록 계산 규칙의 구체화:** 과거 기록을 뒤늦게 추가하거나 수정·삭제할 때 공부량·진도·회독 상태를 일관되게 계산하는 규칙이 필요합니다.
2. **자료 수정 시 데이터 무결성:** 전체 분량을 줄이거나 단위를 변경했을 때 기존 기록의 처리 방법을 명확히 정해야 합니다.
3. **입력 오류 예방:** 전체 분량 초과, 음수, 시작 위치보다 작은 끝 위치, 빈 입력 등을 안내 문구와 함께 검사해야 합니다.
4. **데이터 보존 대책:** LocalStorage는 브라우저·기기별로 분리되며 브라우저 데이터 삭제 등으로 사라질 수 있습니다. 향후 백업·복원 기능을 검토할 필요가 있습니다.
5. **사용성 검증:** 모바일 화면에서 입력과 수정·삭제까지 필요한 조작 수, 버튼 크기, 기록 목록의 가독성을 실제 사용자 관점에서 점검해야 합니다.
6. **테스트 체계 보강:** 다양한 회독과 부분 복습 조합을 포함한 테스트 사례를 마련하고, 기능 수정 후 기존 기능의 정상 작동 여부를 재검증해야 합니다.

※ 위 내용은 개선 과제이며, 범위 제외 항목을 이번 버전에 추가 구현한다는 뜻은 아닙니다.

## 6. 결론

학습 진도 관리 앱은 여러 공부 자료의 진행 상황과 반복 학습 내역을 간단하게 기록·확인하기 위해 기획한 프로젝트입니다. 기능을 단순히 나열하는 데 그치지 않고, PRD로 입력 항목과 동작 규칙을 정의한 다음 TODO 리스트로 개발 순서와 확인 기준을 나누었습니다.

이 과정에서 바이브코딩은 AI에게 짧게 지시하는 것만이 아니라, **개발자가 원하는 결과와 예외 조건을 명확히 전달하고 단계별로 검증하는 과정**이라는 점을 확인할 수 있습니다. 최종 완성 여부는 기능 테스트와 실제 사용 결과로 판단하며, 이후에도 데이터 안정성과 사용성을 중심으로 개선할 계획입니다.
