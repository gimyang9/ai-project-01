# 학습 관리 앱 2.0


## 1. 제작한 것 소개

**학습 관리 앱 2.0**은 교재·문제집·강의의 진도와 회독을 기록하고, 시험 일정과 실제 학습 이력을 바탕으로 **오늘의 권장 학습량, 복습할 범위, 예상 완료일**을 보여 주는 반응형 학습 관리 웹앱입니다. 대학생이나 취준생처럼 여러 시험을 병행하는 사용자를 대상으로 합니다.

### 핵심 기능

- **학습 자료 관리:** 자료 등록·수정·삭제, 유형별 단위, 진도·회독·부분 복습 기록, 메모, 목표 완료일, 일시 중단·완료·보관·복원
- **시험 관리:** 시험 등록·수정, 선택적 시험일 및 D-Day, 한 자료의 여러 시험 연결, 단일 우선 시험, 쉬는 날짜·요일, 시험 중단·재개·재응시
- **학습 계획:** 실제 남은 분량과 학습 가능일을 이용한 자동 권장량, 사용자 지정 일일 분량, 계획상 예상 완료일·실제 속도 예상일·목표일의 구분
- **이해도 기반 복습:** 쉬움/보통/어려움, 1·3·7일 기본 간격, 이후 간격 조정, 밀린 복습·시험 전 집중 복습·중복 추천 통합
- **학습 통계:** 주·월·최근 3/6개월 통계, 학습 캘린더와 날짜별 기록, 현재 회독 학습 속도
- **시각화·테스트:** 자료별 5단계 성장 픽셀 식물, 설정의 독립 ON/OFF 가상 데이터 시연 모드

## 5. 느낀 점과 결론

### 5.1 느낀 점

실습 과제 시 구현한 v1은 비교적 단순한 기능을 중심으로 제작했기 때문에 AI에게 원하는 내용을 설명하고 결과물을 확인하는 방식만으로도 큰 어려움 없이 개발할 수 있었습니다.
하지만 이번 중간고사 과제로 구현한 v2에서는 기능을 확장하고 UI를 개선하면서 처음에는 예상하지 못했던 문제들을 많이 경험했습니다.

#### 5.1.1 반응형 UI 구현의 어려움

가장 어려웠던 부분 중 하나는 화면 크기에 따른 레이아웃 조정이었습니다. 모바일과 PC에서 모두 정상적으로 작동해야 하는 앱이다 보니 단순히 화면을 보기 좋게 만드는 것만으로는 부족했습니다. 같은 PC 환경에서도 브라우저의 너비에 따라 요소의 크기나 정렬이 달라졌고, 특정 화면에서는 자연스럽게 보이던 구성이 다른 화면에서는 어색해지는 경우가 많았습니다.

처음에는 이러한 부분도 AI가 알아서 처리할 수 있을 것이라고 생각했지만, 실제로는 원하는 결과를 얻기 어려웠습니다. 결국 Live Server로 화면을 수시로 확인하면서 여백이나 크기, 정렬 등을 구체적인 수치로 지정해 수정해야 했습니다.

#### 5.1.2 PRD와 Todo 리스트를 통한 개발 과정 관리

PRD와 Todo 리스트의 필요성도 v1에 비해 훨씬 크게 느꼈습니다. v1에서는 기능이 단순하고 작업량도 많지 않아 처음 작성한 계획을 수정할 일이 거의 없었습니다.

반면 v2에서는 기능이 늘어나며 개발 기간이 길어지면서 어떤 작업을 완료했고, 무엇이 남아 있는지 기억하는 것조차 쉽지 않았습니다. 특히 기존 기능을 수정하거나 새로운 기능을 추가할 때는 해당 기능의 여부 및 진행 상황을 정확하게 파악하는 것이 중요했습니다.

이 과정에서 PRD와 Todo 리스트를 지속적으로 수정하고 변경 내역을 기록하는 것이 단순한 문서 작성이 아니라, 개발을 체계적으로 이어 나가기 위한 중요한 과정이라는 것을 알게 되었습니다.

#### 5.1.3 AI 활용의 한계와 직접 검증의 중요성

이번 프로젝트에서는 AI에게 작업을 맡기는 것만큼이나 결과물을 직접 확인하고 수정하는 과정이 중요하다는 것을 느꼈습니다. 작업을 요청할 때마다 관련 기능을 점검하도록 지시했고, 일정 단계까지 개발한 후에는 전체적인 점검을 다시 요청하기도 했습니다. 하지만 이러한 과정을 거쳤음에도 실제 화면에서는 정렬이 어색하거나 사용하기 불편한 부분이 남아 있었습니다.

특히 시각적으로 거슬리는 요소나 미묘한 레이아웃의 차이는 AI의 점검만으로 완전히 해결하기 어려웠습니다. 그래서 다양한 상황을 확인할 수 있도록 AI에게 테스트 케이스를 작성하게 하고, 이를 바탕으로 개발자 테스트 모드를 구현했습니다. 실제 UI에 테스트 데이터를 적용해 보면서 기능이 정상적으로 작동하는지뿐만 아니라 화면에 어떻게 표현되는지도 직접 확인할 수 있었습니다. 이를 통해 AI가 문제가 없다고 판단하는 것과 실제 사용자가 불편함 없이 사용할 수 있는 것은 별개의 문제라는 것을 느꼈습니다.

또한 모든 작업을 AI에게 맡기는 것이 반드시 효율적인 것은 아니었습니다. 복잡한 기능을 구현할 때는 AI의 도움을 크게 받을 수 있었지만, 간단한 문구나 스타일을 수정하는 작업까지 매번 에이전트에게 요청하다 보면 오히려 시간과 사용량이 더 많이 소모되는 경우도 있었습니다. 이런 작업은 직접 코드를 수정하는 편이 빠르고 편리하기도 했습니다.

결국 **AI의 결과물을 그대로 받아들이기보다 직접 검증하고, 작업의 성격에 따라 AI에게 맡길 부분과 직접 처리할 부분을 구분하는 것이 중요하다**고 생각했습니다.

### 5.2 결론

v1이 AI를 활용해 아이디어를 실제 프로그램으로 구현해 보는 경험이었다면, v2은 더 복잡한 프로젝트를 체계적으로 관리하고 AI와 협업하는 방법을 배운 과정이었습니다.

이번 프로젝트를 통해 바이브 코딩은 단순히 AI에게 개발을 맡기는 방식이 아니라, **사람의 기획과 판단을 바탕으로 AI의 능력을 적절하게 활용하는 개발 방식**이라는 점을 알게 되었습니다.
