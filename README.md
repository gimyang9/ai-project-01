# 학습 관리 앱 v2


## 1. 제작한 것 소개

**학습 관리 앱 v2**은 교재·문제집·강의의 진도와 회독을 기록하고, 시험 일정과 실제 학습 이력을 바탕으로 **오늘의 권장 학습량, 복습할 범위, 예상 완료일**을 보여 주는 반응형 학습 관리 웹앱입니다. 대학생이나 취준생처럼 여러 시험을 병행하는 사용자를 대상으로 합니다.

### 핵심 기능

- **학습 자료 관리:** 자료 등록·수정·삭제, 유형별 단위, 진도·회독·부분 복습 기록, 메모, 목표 완료일, 일시 중단·완료·보관·복원
- **시험 관리:** 시험 등록·수정, 선택적 시험일 및 D-Day, 한 자료의 여러 시험 연결, 단일 우선 시험, 쉬는 날짜·요일, 시험 중단·재개·재응시
- **학습 계획:** 실제 남은 분량과 학습 가능일을 이용한 자동 권장량, 사용자 지정 일일 분량, 계획상 예상 완료일·실제 속도 예상일·목표일의 구분
- **이해도 기반 복습:** 쉬움/보통/어려움, 1·3·7일 기본 간격, 이후 간격 조정, 밀린 복습·시험 전 집중 복습·중복 추천 통합
- **학습 통계:** 주·월·최근 3/6개월 통계, 학습 캘린더와 날짜별 기록, 현재 회독 학습 속도
- **시각화·테스트:** 자료별 5단계 성장 픽셀 식물, 설정의 독립 ON/OFF 가상 데이터 시연 모드

````markdown
# 차곡차곡 데이터·기록 보호

차곡차곡 앱의 데이터 관련 작업에서 기존 기록과 사용자 설정을 보존하고, 변경 전후의 영향 범위와 검증 결과를 기록합니다.

이 스킬은 데이터 보호와 작업 이력 관리를 담당하며, 계산 정확성이나 화면 레이아웃 전체를 검증하지 않습니다.

이 스킬은 프로젝트용으로 개선한 버전이며, 과거 `CG-SKILL-001~012` 기록의 원문을 복원한 것이 아닙니다. 실제 사용 이전의 작업에 개선된 스킬을 소급 적용했다고 기록하지 않습니다.

## 1. 작업 범위와 보호 대상 확인

작업 전에 다음 내용을 확인합니다.

1. **최신 사용자 요청:** 변경 목적과 명시된 제한 사항
2. **진행 상황:** `PROGRESS.md`, 관련 요구사항과 후속 결정
3. **작업 번호:** 관련 TODO 또는 변경 이력
4. **저장 구조:** 대상 저장 키, 데이터 버전, 관련 코드
5. **기대 동작:** 변경 후 정상적으로 유지되어야 할 상태
6. **검사 조건:** 합성 데이터, 기준일, 관련 테스트

최신 사용자 지시를 우선 적용합니다.

문서나 스킬의 수정 요청을 앱 구현·빌드·배포 승인으로 해석하지 않습니다.

사용자가 보호 대상으로 지정한 문서는 읽기 전용으로 취급합니다. Git 커밋과 Push는 사용자가 직접 수행합니다.

`reference/v1`은 읽기 전용으로 유지합니다.

저장 키와 데이터 구조는 현재 소스에서 다시 확인하고, 과거 보고서의 통과 횟수나 상태를 현재 검증 결과로 재사용하지 않습니다.

## 2. 데이터 보존 규칙

데이터를 수정하거나 저장 구조를 변경할 때 다음 규칙을 확인합니다.

### 2.1 원본 기록 보존

- 자료와 기록의 고유 ID
- 기록 날짜, 시각, 순서
- 학습 단위와 범위
- 이해도 및 평가 이력
- 회독별 학습 기록
- 기존 데이터의 알 수 없는 필드

파생된 학습·복습 추천값을 계산하기 위해 원본 평가 기록을 덮어쓰지 않습니다.

알 수 없는 필드는 기존 데이터와의 호환성을 고려하여 보존 방침을 먼저 확인합니다.

### 2.2 학습과 회독

- 부분 복습은 전체 학습 진도와 회독 상태를 변경하지 않습니다.
- 다음 회독으로 넘어가도 이전 회독의 기록을 삭제하지 않습니다.
- 회독 전환 시 기존 이력과 새 회독의 기록을 구분합니다.
- 기록 수정·삭제가 다른 기록에 의도치 않은 영향을 주지 않는지 확인합니다.

### 2.3 사용자 수동 설정

다음 수동 설정은 자동 추천보다 우선합니다.

- 사용자가 직접 지정한 학습량
- 수동 복습일
- 자료별 메모
- 목표 완료일

자동 계획이나 추천을 다시 계산하더라도 기존 수동 설정을 임의로 초기화하거나 덮어쓰지 않습니다.

### 2.4 시험과 학습 상태

- 자료의 직접 중단 설정은 시험에 따른 자동 중단보다 우선합니다.
- 하나의 자료가 여러 시험에 연결된 상태를 보존합니다.
- 시험별 활성 연결과 계속 학습 선택을 구분합니다.
- 특정 시험만 재개했을 때 다른 시험의 상태가 변경되지 않는지 확인합니다.

### 2.5 복습 기록과 저장

- 일반 복습과 시험 전 복습의 중복 표시를 실제 기록 중복과 구분합니다.
- 복습 완료 시 실제 기록이 한 번만 생성되는지 확인합니다.
- 읽기와 검증, 쓰기가 성공한 후에만 화면 상태를 확정합니다.
- 읽을 수 없는 데이터나 지원하지 않는 버전은 자동으로 덮어쓰지 않습니다.

## 3. 변경 전 기준 수집

수정 전에 `scripts/inspect-boundary.ps1`을 실행해 파일과 저장 경계의 기준을 수집합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File skills/chagok-data-guard/scripts/inspect-boundary.ps1 -ProjectRoot .
```

수집한 JSON 결과는 사용자가 허용한 새 결과 폴더에 `before.json`으로 보관합니다.

이 스크립트는 조회 전용이며 실제 브라우저 저장소에 접근하지 않습니다.

실행 규칙:

- 사용자 브라우저의 저장 데이터를 수정하거나 초기화하지 않습니다.
- 보호 문서와 앱·자산 파일의 변경 경계를 수집합니다.
- 시스템 전체의 실행 정책을 변경하지 않습니다.
- 결과 파일은 허용된 폴더에만 저장합니다.
- 기존 파일을 자동 복구하거나 동기화하지 않습니다.

## 4. 관련 데이터 검증

변경 범위와 관련된 사례만 선택합니다.

### 4.1 저장 데이터

- 저장 후 새로고침 시 데이터 유지
- 백업 및 복원 왕복 후 데이터 일치
- 손상된 JSON 처리
- 지원하지 않는 데이터 버전 처리
- 저장 실패 시 기존 데이터 보존
- 변경 충돌 시 데이터 보호

### 4.2 학습 및 복습 기록

- 학습 기록 수정과 삭제
- 부분 복습과 전체 진도의 독립성
- 회독 전환 후 과거 이력 보존
- 이해도 및 복습 범위 기록 유지
- 추천 완료 후 중복 기록 생성 방지

### 4.3 시험 상태

- 여러 시험과 연결된 자료의 상태
- 자료 직접 중단과 시험 자동 중단의 우선순위
- 시험별 계속 학습 선택
- 특정 시험만 재개하는 경우
- 다른 시험과 연결된 데이터의 보존

실제 사용자 데이터 대신 합성 메모리 저장소 또는 새 임시 Chrome 프로필을 사용합니다.

사용자 브라우저나 사이트 저장소를 초기화하지 않습니다.

## 5. 기존 테스트 실행

관련 테스트는 실제 프로젝트 파일을 확인한 후 선택합니다.

예시:

- `tests/study-data.test.cjs`
- `tests/study-app.test.cjs`
- `tests/final-integration.test.cjs`

실제로 존재하는 파일과 현재 변경 범위를 기준으로 실행합니다.

Node.js 실행 경로는 환경에서 확인합니다. PATH에서 명령을 찾을 수 없다는 이유만으로 앱 오류라고 판단하지 않습니다.

실행 불가 또는 중단된 검사는 미검증으로 기록합니다.

기존 테스트가 실패하더라도 테스트를 삭제하거나 결과를 임의로 통과 처리하지 않습니다.

powershell -NoProfile -ExecutionPolicy Bypass -File skills/chagok-data-guard/scripts/inspect-boundary.ps1 -ProjectRoot . -BaselinePath <before.json>
```

변경 전후 결과를 비교하여 다음을 확인합니다.

1. 의도한 소스 파일만 변경되었는가?
2. 보호 대상 파일이 변경되지 않았는가?
3. 예상하지 못한 저장 경계 변경이 발생했는가?
4. 사용자 설정과 기존 기록이 유지되는가?
5. 추가 검증이 필요한 영역이 있는가?

파일 해시가 동일하다는 사실만으로 사용자 데이터의 무손실을 보장하지 않습니다.

또한 정적 패턴 검사로는 간접적인 저장 함수 호출을 모두 발견하지 못할 수 있으므로, 소스 분석 결과와 실제 합성 실행 결과를 구분합니다.

검증 과정에서 앱이나 문서를 자동 복구·수정하지 않습니다.

## 7. 검증 결과 판정

각 검사 결과를 다음 세 가지로 구분합니다.

| 판정 | 기준 |
|---|---|
| 통과 | 실제 검사를 수행했고 기대 동작과 일치함 |
| 실패 | 데이터 변경, 손실, 중복 등 불일치가 확인됨 |
| 미검증 | 실행 불가, 검사 미수행, 근거 부족 등으로 확인하지 못함 |

검증 근거의 종류도 함께 기록합니다.

- 소스 검토
- 합성 데이터 실행
- 격리 브라우저
- 실제 기기

통과 판정은 실제로 수행한 검사 범위에만 적용합니다.

문제를 발견하면 실패한 검사를 제거하거나 앱을 자동 수정하지 않고, 재현 조건·영향 범위·검증 한계를 보고합니다.

## 8. 다른 검증 스킬과의 연계

작업 내용에 따라 필요한 검사만 선택합니다.

- `chagok-learning-check`: 학습량, 예상 완료일, 복습 간격 등 계산의 정확성
- `chagok-ui-regression`: 화면 배치, 모달, 입력·저장·취소 조작의 회귀
- `chagok-data-guard`: 원본 데이터, 학습 기록, 수동 설정의 보존

모든 작업에 세 스킬의 전체 검사를 강제하지 않습니다.

PWA 감사, 캐시 검증, 빌드 및 게시 작업은 이 스킬의 범위에 포함하지 않습니다.

## 9. 스킬 활용 이력 기록

실제 프로젝트 작업에서 스킬을 적용한 경우에만 기존 활용 로그에 기록합니다.

대상 파일:

- `docs/skill-usage-log.md`
- `docs/skill-usage-log.jsonl`

기존 기록은 보존하고 새로운 실제 적용 사례만 고유 ID로 추가합니다.

### 필수 기록 항목

- `id`: 고유 적용 ID
- `date`: 실제 적용 날짜
- `skill`: 사용한 스킬
- `skill_source`: 스킬 출처
- `task`: 수행 작업
- `todo_refs`: 관련 작업 번호
- `actions`: 수행한 작업
- `evidence`: 실행 명령과 검증 근거
- `result`: 결과 요약
- `outcome`: 작업 결과
- `limitations`: 검증 한계

요약 결과는 다음 값을 사용합니다.

- `passed`: 수행한 필수 검사가 통과한 경우
- `limited`: 일부 항목이 미검증인 경우
- `failed`: 실패가 확인된 경우

검사별 상세 판정은 근거와 연결하여 기록합니다.

### 활용 기록 도구

`scripts/record-usage.cjs`를 사용합니다.

```powershell
node skills/chagok-data-guard/scripts/record-usage.cjs --entry <JSON파일> --root .
```

실제 기록을 추가할 때만 `--write` 옵션을 사용합니다.

```powershell
node skills/chagok-data-guard/scripts/record-usage.cjs --entry <JSON파일> --root . --write
```

도구는 중복 ID, 필수 항목 누락, 잘못된 필드를 거부합니다.

과거 누락 ID를 자동 생성하거나 기존 로그 형식을 임의로 변환하지 않습니다.

두 로그 파일에 대한 완전한 원자적 트랜잭션은 보장되지 않으므로 기록에 실패하면 복구 및 부분 기록 메시지를 확인합니다.

스킬 제작·수정·구문 검사와 실제 앱에 적용한 검증 기록을 구분합니다.
````

````markdown
# 차곡차곡 학습·복습 계산 검증

차곡차곡 앱의 학습 계획 및 복습 계산 결과를 고정된 기준일과 독립적으로 계산한 기대값을 사용해 검증합니다.

계산 정책 변경이나 오류 수정 후 기존 계산이 정상적으로 유지되는지 확인하는 것이 목적입니다.

단순 화면·문구 수정에는 전체 계산 검사를 강제하지 않습니다. 검증 과정에서 앱 코드와 기존 테스트 결과를 임의로 수정하지 않습니다.

## 1. 계산 정책 및 검사 범위 확인

검사 전에 다음 자료를 확인합니다.

1. **최신 계산 정책:** 사용자가 확정한 학습·복습 계산 규칙
2. **관련 문서:** `docs/PRD-updates.md`와 관련 보고서
3. **검사 대상:** root 또는 dist의 순수 계산 모듈
4. **기준일과 시간대:** 날짜 계산에 사용할 고정 기준
5. **합성 입력:** 학습량, 진도, 학습 기록, 시험일, 복습 범위 등
6. **검사 범위:** 변경된 계산과 영향을 받을 수 있는 기존 계산

최신 사용자 결정과 문서·테스트의 기대값이 충돌하면 임의로 정답을 선택하지 않습니다.

정책의 근거가 불명확한 항목은 미검증으로 기록하고 충돌 내용을 보고합니다.

실제 사용 이전의 개발에 이 스킬을 적용했다고 소급 기록하지 않습니다.

## 2. 독립적인 기대값 작성

검사에서는 다음 두 가지를 구분합니다.

- **원본 불변성:** 검증으로 기존 데이터와 상태가 변경되지 않았는가?
- **계산 정확성:** 계산 결과가 정책에 따른 정답과 일치하는가?

구현 함수를 다시 호출한 결과를 기대값으로 사용하지 않습니다.

작은 달력의 날짜 열거, 정수 위치 집합, 독립적으로 작성한 계산식 등 검사 대상 구현과 다른 방식으로 기대값을 구합니다.

기존 테스트가 실패해도 테스트를 삭제하거나 기대값을 임의로 변경해 통과시키지 않습니다.

## 3. 검사 실행

`scripts/check-learning.cjs`를 사용해 root 또는 dist의 순수 계산 모듈을 메모리에서 실행합니다.

브라우저, 사용자 저장소, 앱 파일은 변경하지 않으며 결과는 새로운 파일로만 저장합니다.

```powershell
node skills/chagok-learning-check/scripts/check-learning.cjs --root . --source root --today <기준일:YYYY-MM-DD> --out <새결과.json>
```

배포 사본도 검사 대상이면 `--source dist`로 별도 실행합니다.

실행 규칙:

- `--today`에 고정 기준일을 반드시 지정합니다.
- 운영체제의 시계는 변경하지 않습니다.
- Node.js가 PATH에 없으면 확인된 실행 파일 경로를 사용합니다.
- 실행 명령, 대상 경로, 런타임 환경을 결과에 기록합니다.
- 기존 결과 파일을 덮어쓰지 않습니다.

### 정책 프로필 확인

내장 검사는 현재 회독 기준 정책과 계획·실제 예상 완료일 분리를 대상으로 합니다.

실행 결과의 `policyProfile`은 검사 정책의 식별자이며 스킬의 작성일을 의미하지 않습니다.

1/3/7일 복습 간격, 간격 배수, 현재 회독 기준 등 정책이 변경되었다면 다음 순서로 처리합니다.

1. 최신 사용자 결정과 관련 문서를 확인합니다.
2. 기존 검사 프로필과 새 정책의 차이를 정리합니다.
3. 과거 정책과 다르다는 이유만으로 앱을 실패 처리하지 않습니다.
4. 필요한 경우 이 스킬 폴더의 검사 사례만 수정합니다.
5. 정책 충돌이 해결되지 않은 검사는 미검증으로 남깁니다.

앱 소스나 기존 정책 문서를 검증 과정에서 자동 수정하지 않습니다.

## 4. 계산 검증 항목

변경 내용과 관련된 항목을 선택하여 검사합니다.

### 4.1 학습 계획 및 권장 학습량

- 자동 학습 계획과 수동 설정 계획
- 남은 분량에 따른 권장 학습량
- 오늘 학습한 분량과 남은 학습량
- 이미 반영한 학습량의 중복 계산 방지
- 학습 가능 요일과 쉬는 날
- 계획 변경 후 남은 분량의 재계산

### 4.2 예상 완료일

다음 두 계산을 독립적으로 확인합니다.

**계획상 예상 완료일**
- 설정된 학습 계획과 예정 학습량을 기준으로 계산
- 자동·수동 계획의 차이 반영
- 계획 변경에 따른 예상일 갱신

**실제 예상 완료일**
- 실제 학습 기록과 학습 속도를 기준으로 계산
- 현재 회독에 해당하는 기록 사용
- 기록이 부족할 때의 정책 적용
- 계획상 예상일과의 혼동 여부 확인

두 예상일은 각각의 계산 기준과 기대값을 별도로 기록합니다.

### 4.3 복습 일정과 범위

- 최초 학습 및 복습 후 다음 추천일
- 정책에 따른 복습 간격과 배수
- 이전 복습 간격과 이해도에 따른 계산
- 복습 범위의 중복과 겹침 처리
- 동일 범위에 대한 최신 기록 반영
- 복습 일정 변경 후 기존 이력 보존

현재 구현에서 연속 성공 횟수는 별도로 관리하며 복습 간격 계산에는 사용하지 않습니다.

겹치는 범위는 가능한 경우 작은 정수 위치 집합으로 변환해 독립적으로 검증합니다.

### 4.4 경계 및 예외 사례

변경과 관련된 기존 테스트를 선택해 다음 경계를 보완합니다.

- 학습 기록이 없거나 부족한 상태
- 계획 완료 또는 남은 분량이 없는 상태
- 날짜가 변경되는 경계
- 매우 큰 학습량이나 긴 기간
- 여러 시험과 연결된 학습 자료
- 미리보기 계산 후 원본 상태의 불변성

내장 사례만 실행하고 모든 계산 정책을 검증했다고 표현하지 않습니다.

## 5. 검사 결과 판정
````

````markdown
# 차곡차곡 UI 회귀 검증

차곡차곡 앱의 화면이나 사용자 조작을 변경한 후, 기존 기능과 화면 배치가 의도치 않게 달라지지 않았는지 격리된 Chrome 환경에서 검증합니다.

이 스킬은 검증과 결과 보고만 담당합니다. 앱 코드나 디자인을 자동으로 수정하지 않습니다.

## 1. 검사 범위 확정

검사를 시작하기 전에 다음 항목을 확인합니다.

1. **수정 대상:** 이번 변경으로 달라져야 하는 화면과 조작
2. **유지 대상:** 기존 상태를 보존해야 하는 화면과 기능
3. **기준 화면:** 변경 전 화면 또는 사용자가 제시한 기준
4. **검사 데이터:** 긴 이름, 많은 항목, 스크롤이 필요한 합성 사례
5. **검사 환경:** 화면 너비·높이, 필요한 경우 브라우저 확대와 키보드 조작

요청이 특정 화면에 한정되면 다른 화면의 변경을 승인한 것으로 해석하지 않습니다.

기준 화면이나 필수 조건이 없으면 확인 가능한 범위만 검사하고, 비교할 수 없는 항목은 미검증으로 남깁니다.

## 2. 검증 환경 준비

실사용 브라우저와 저장소를 보호하기 위해 독립된 테스트 환경을 사용합니다.

- 새 임시 Chrome 프로필과 루프백 서버를 사용합니다.
- 합성 테스트 데이터는 임시 프로필에만 생성합니다.
- 사용자 브라우저의 쿠키, LocalStorage, SessionStorage를 변경하지 않습니다.
- README.md, TODO.md, PRD.md 및 앱 소스·이미지·캐시·설정 파일을 수정하지 않습니다.
- 사용자 사이트 데이터 삭제를 문제 해결 방법으로 사용하지 않습니다.
- 테스트 환경과 프로필 경로를 결과에 기록합니다.

Node.js와 Chrome 실행 경로를 먼저 확인합니다.

브라우저 준비에 실패하면 검증을 중단하고 해당 항목을 **미검증**으로 기록합니다. 자동 설치, 권한 확대, 시스템 정책 변경, 캐시 빌드는 수행하지 않습니다.

`--allow-test-no-sandbox`는 도구가 생성한 임시 프로필에서 격리 환경 오류를 진단할 때만 사용하는 선택 옵션이며, 기본값으로 사용하지 않습니다.

## 3. 검사 실행

`scripts/run-ui.cjs`는 서버 실행, 브라우저 준비, 검사 대기, 결과 저장을 담당합니다.

`scripts/chagok-cases.cjs`에는 앱의 실제 조작을 검증하는 사례가 정의되어 있습니다.

요청과 관련된 검사 그룹만 선택합니다.

```powershell
node skills/chagok-ui-regression/scripts/run-ui.cjs --root . --chrome <chrome.exe> --route /index.html --groups home,plan --sizes 320x400,375x700,1440x900 --capture --out <새결과폴더>
```

지원 그룹:

- `home`: 홈 화면
- `plan`: 학습 계획 관련 화면
- `stats`: 통계 화면

root와 dist가 모두 검사 대상이면 `/dist/index.html`을 별도 결과 폴더에서 실행합니다.

다른 화면의 검사가 필요하면 `--cases <사례모듈.cjs>`로 승인된 로컬 검사 모듈을 지정합니다. 신뢰할 수 없는 외부 코드는 실행하지 않습니다.

실제로 선택한 그룹과 화면 크기만 검증한 것으로 기록합니다.

## 4. 검증 항목

### 4.1 반응형 레이아웃

변경과 관계있는 화면 크기 및 CSS 경계에서 실제 렌더링을 확인합니다.

- 좁은 모바일 화면과 낮은 화면 높이
- 데스크톱 화면과 필요한 중간 너비
- 긴 이름의 줄바꿈·말줄임·영역 넘침
- 많은 항목이 표시될 때의 배치와 스크롤
- 모달의 높이, 내부 스크롤, 버튼 접근성
- 화면 끝까지 이동했을 때 콘텐츠 잘림 여부

필요한 경우 키보드 조작과 실제 브라우저 확대를 추가합니다.

브라우저 확대는 단순한 뷰포트 크기 변경과 구분해 기록합니다.

### 4.2 입력 및 저장 동작

입력 흐름이 포함된 경우 다음 동작을 개별적으로 검증합니다.

1. **미리보기:** 입력을 변경하면 즉시 갱신되는지 확인합니다.
2. **저장 전 상태:** 미리보기만으로 앱 상태와 LocalStorage·SessionStorage의 저장값이 변경되지 않는지 확인합니다.
3. **취소·닫기:** 변경 사항이 저장되지 않고 기존 설정이 유지되는지 확인합니다.
4. **잘못된 입력:** 유효하지 않은 입력이 기존 설정을 손상시키지 않는지 확인합니다.
5. **저장 실패:** 실패 상황에서도 기존 저장 데이터가 보존되는지 확인합니다.
6. **정상 저장:** 변경 사항이 실제 화면과 저장소에 반영되는지 확인합니다.
7. **재로드:** 새로고침 후 저장된 설정이 유지되는지 확인합니다.

실행하지 않은 검사는 통과로 처리하지 않고 미검증으로 기록합니다.

### 4.3 기존 화면 유지

검사 범위에서 유지 대상으로 지정한 화면을 기준 화면과 비교합니다.

- 화면 내용 및 주요 구성 요소
- 레이아웃과 정렬
- 주요 버튼과 입력 요소의 위치
- 화면 이동 및 기존 조작 동작

스크린샷을 직접 확인하고, 자동 위치·크기 검사와 실제 버튼 조작을 함께 판단합니다.

콘솔 오류가 없거나 스크린샷을 생성했다는 사실만으로 UI 전체가 정상이라고 판정하지 않습니다.

## 5. 결과 판정

각 검사 항목을 다음 세 가지 상태로 구분합니다.

| 판정 | 기준 |
|---|---|
| 통과 | 실제 검사를 수행했고 기대 결과와 일치함 |
| 실패 | 잘림, 요소 누락, 저장 전 상태 변경 등 불일치가 관찰됨 |
| 미검증 | 환경 오류, 검사 미실행, 기준 부재 등으로 판정할 수 없음 |

실패한 검사를 삭제하거나 결과를 통과로 변경하지 않습니다.

문제를 발견해도 앱 소스와 CSS를 자동 수정하지 않습니다. 수정이 필요하면 원인과 재현 조건을 보고합니다.

원본 화면을 캡처하고 보존합니다. 토스트나 내비게이션을 숨기거나 캡처 영역을 잘랐다면 해당 사실을 별도로 기록합니다.

Chrome의 모바일 너비 검증은 실제 iPhone Safari 또는 PWA 동작 검증을 대체하지 않습니다.
````

### 4.1. 데이터·기록 보호 — `chagok-data-guard`

**제작 이유:** v2에서는 v1보다 복잡한 기능을 추가했다. 새로운 기능을 구현하거나 기존 기능을 수정하는 과정에서 이전 학습 기록이 사라지거나 사용자가 직접 설정한 값이 변경되지 않도록 하는 것이 중요했다.

예를 들어 2회독을 시작하더라도 1회독의 학습 기록은 남아 있어야 하고, 사용자가 직접 지정한 학습량이나 복습일은 자동 추천 기능 때문에 덮어써지면 안 된다.

이처럼 반드시 지켜야 할 데이터 보존 규칙을 반복해서 설명하지 않도록 스킬을 제작했다. 이후에는 변경 전후의 파일을 비교하고 실제 검증 결과를 기록할 수 있도록 기존 스킬을 개선했다.

**실제 사용:** 개발 과정에서 학습 계획과 복습 기능을 수정할 때 기존 기록과 설정을 보호하는 데 활용했다.

예를 들어 계획상 예상 완료일과 실제 예상 완료일을 분리하는 작업에서는 계산 기능뿐 아니라 기존 학습 기록, 수동 설정, 저장 구조가 유지되는지도 확인했다.

또한 식물 이미지나 화면 구성만 수정하는 작업에서는 학습 데이터와 관련된 코드까지 불필요하게 변경되지 않았는지 점검하는 데 사용했다.

### 4.2. 학습·복습 계산 검증 — `chagok-learning-check`

**제작 이유:** v2에서는 학습량 추천과 예상 완료일 계산 기능이 복잡해졌다. 남은 학습 분량뿐 아니라 공부할 요일, 쉬는 날, 오늘 공부한 분량, 사용자가 직접 설정한 학습량 등을 고려해야 했기 때문이다.

특히 계획에 따라 계산하는 예상 완료일과 실제 학습 속도 기준으로 계산하는 예상 완료일은 서로 다른 기준을 사용한다. 복습 추천 날짜 역시 이해도와 이전 복습 기록 등에 따라 달라진다.

이처럼 여러 조건이 포함된 계산은 화면에 결과가 정상적으로 표시된다는 이유만으로 정확하다고 판단하기 어려웠다. 따라서 앱이 계산한 결과를 별도의 기대값과 비교하여 검증할 수 있도록 스킬을 제작했다.

**실제 사용:** 학습 계획과 복습 기능을 개발한 이후, 계산 결과가 의도한 정책에 맞게 작동하는지 확인하는 데 사용했다.

자동·수동 학습 계획, 오늘 학습량 반영, 계획상 예상 완료일과 실제 예상 완료일의 구분, 복습 간격 및 범위 겹침 등을 검사했다. 이때 앱의 계산 결과를 그대로 정답으로 사용하지 않고, 별도로 구한 기대값과 비교하여 계산의 정확성을 확인했다.

검사는 프로젝트의 원본 실행 경로인 root와 배포용 파일인 dist에서 각각 진행했으며, 각각 20건의 테스트가 통과했다.

### 4.3. 화면·조작 회귀 검증 — `chagok-ui-regression`

**제작 이유:** 학습 관리 앱은 모바일과 PC에서 모두 사용할 수 있도록 개발했다. 그런데 화면의 너비나 높이가 달라지면 같은 요소라도 정렬이나 크기가 크게 달라지는 문제가 있었다.

특히 모바일에서는 정상적으로 보이던 화면이 PC에서 어색하게 배치되거나, 화면 높이가 낮을 때 모달의 일부 내용이나 버튼이 가려질 수 있었다. 또한 상세 계획 화면을 수정한 뒤 홈 화면의 기존 구성을 다시 복원해야 했던 경우도 있었다.

한 부분을 수정했을 때 다른 부분에 문제가 발생하는 회귀 오류에 대해서, 화면을 수정할 때마다 이러한 문제를 일정한 기준으로 확인하기 위해 스킬을 제작했다.

**실제 사용:** 스킬 제작 이후 홈 화면, 상세 학습 계획, 미리보기, 저장·취소, 통계 화면의 동작을 검사했다. 320×400, 375×700, 1440×900 크기의 브라우저 화면에서 실제 요소의 배치와 조작을 확인했다.

다만 Chrome에서 화면 크기를 변경하여 진행한 검사이므로 실제 iPhone Safari나 설치된 PWA에서 동일하게 작동한다고 단정할 수는 없다.


## 5. 느낀 점과 결론

### 5.1 느낀 점

실습 과제 시 구현한 v1은 비교적 단순한 기능을 중심으로 제작했기 때문에 AI에게 원하는 내용을 설명하고 결과물을 확인하는 방식만으로도 큰 어려움 없이 개발할 수 있었습니다.
하지만 이번 중간고사 과제로 구현한 v2에서는 기능을 확장하고 UI를 개선하면서 처음에는 예상하지 못했던 문제들을 많이 경험했습니다.

#### 5.1.1 반응형 UI 구현의 어려움

가장 어려웠던 부분 중 하나는 화면 크기에 따른 레이아웃 조정이었습니다. 모바일과 PC에서 모두 정상적으로 작동해야 하는 앱이다 보니 단순히 화면을 보기 좋게 만드는 것만으로는 부족했습니다. 같은 PC 환경에서도 브라우저의 너비에 따라 요소의 크기나 정렬이 달라졌고, 특정 화면에서는 자연스럽게 보이던 구성이 다른 화면에서는 어색해지는 경우가 많았습니다.

처음에는 이러한 부분도 AI가 알아서 처리할 수 있을 것이라고 생각했지만, 실제로는 원하는 결과를 얻기 어려웠습니다. 결국 Live Server로 화면을 수시로 확인하면서 여백이나 크기, 정렬 등을 구체적인 수치로 지정해 수정해야 했습니다.

#### 5.1.2 PRD와 Todo 리스트를 통한 개발 과정 관리

PRD와 Todo 리스트의 필요성도 v1에 비해 훨씬 크게 느꼈습니다. v1에서는 기능이 단순하고 작업량도 많지 않아 처음 작성한 계획을 수정할 일이 거의 없었습니다.

반면 v2에서는 기능이 늘어나며 개발 기간이 길어지면서 어떤 작업을 완료했고, 무엇이 남아 있는지 기억하는 것조차 쉽지 않았습니다. 특히 기존 기능을 수정하거나 새로운 기능을 추가할 때는 해당 기능의 여부 및 진행 상황을 정확하게 파악하는 것이 중요했습니다.

이 과정에서 PRD와 Todo 리스트를 지속적으로 수정하고 변경 내역을 기록하는 것이 단순한 문서 작성이 아니라, 개발을 체계적으로 이어 나가기 위한 중요한 과정이라는 것을 알게 되었습니다.

#### 5.1.3 AI 활용의 한계와 직접 검증의 중요성

이번 프로젝트에서는 AI에게 작업을 맡기는 것만큼이나 결과물을 직접 확인하고 수정하는 과정이 중요하다는 것을 느꼈습니다. 작업을 요청할 때마다 관련 기능을 점검하도록 지시했고, 일정 단계까지 개발한 후에는 전체적인 점검을 다시 요청하기도 했습니다. 하지만 이러한 과정을 거쳤음에도 실제 화면에서는 정렬이 어색하거나 사용하기 불편한 부분이 남아 있었습니다.

특히 시각적으로 거슬리는 요소나 미묘한 레이아웃의 차이는 AI의 점검만으로 완전히 해결하기 어려웠습니다. 그래서 다양한 상황을 확인할 수 있도록 AI에게 테스트 케이스를 작성하게 하고, 이를 바탕으로 개발자 테스트 모드를 구현했습니다. 실제 UI에 테스트 데이터를 적용해 보면서 기능이 정상적으로 작동하는지뿐만 아니라 화면에 어떻게 표현되는지도 직접 확인할 수 있었습니다. 이를 통해 AI가 문제가 없다고 판단하는 것과 실제 사용자가 불편함 없이 사용할 수 있는 것은 별개의 문제라는 것을 느꼈습니다.

또한 모든 작업을 AI에게 맡기는 것이 반드시 효율적인 것은 아니었습니다. 복잡한 기능을 구현할 때는 AI의 도움을 크게 받을 수 있었지만, 간단한 문구나 스타일을 수정하는 작업까지 매번 에이전트에게 요청하다 보면 오히려 시간과 사용량이 더 많이 소모되는 경우도 있었습니다. 이런 작업은 직접 코드를 수정하는 편이 빠르고 편리하기도 했습니다.

결국 **AI의 결과물을 그대로 받아들이기보다 직접 검증하고, 작업의 성격에 따라 AI에게 맡길 부분과 직접 처리할 부분을 구분하는 것이 중요하다**고 생각했습니다.

### 5.2 결론

v1이 AI를 활용해 아이디어를 실제 프로그램으로 구현해 보는 경험이었다면, v2은 더 복잡한 프로젝트를 체계적으로 관리하고 AI와 협업하는 방법을 배운 과정이었습니다.

이번 프로젝트를 통해 바이브 코딩은 단순히 AI에게 개발을 맡기는 방식이 아니라, **사람의 기획과 판단을 바탕으로 AI의 능력을 적절하게 활용하는 개발 방식**이라는 점을 알게 되었습니다.
